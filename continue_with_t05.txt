     AI), or two plans (no-AI product, then AI).
     - Default: one plan, with each phase marked as a checkpoint where the app
       still runs. The spikes go in at the points the doc names: spikes 1–2 in
       phase 1, spike 3 at the start of the AI phase.

  2. DESIGN.md vs Tailwind + shadcn. These two conflict. DESIGN.md ships a UMD
     window.WebAtlas bundle with its own wa-* CSS. The architecture doc says
     Tailwind + shadcn.
     - Default: port the DESIGN.md components into typed .tsx files
       (src/renderer/src/components/wa/). They'd keep bundle.css and the tokens
       as the source of truth, and the UMD bundle wouldn't be used.
     - Tailwind's theme would point at the token CSS variables, so it's used for
       layout only.
     - shadcn would only supply behaviour (Dialog, cmdk Command, Tooltip,
       DropdownMenu), restyled with the tokens so nothing looks like stock
       shadcn.

     logic:
     - each command's apply/invert round-trip, and ghost accept/undo
     - clustering
     - detecting the resource kind (web, video, PDF)
     - the three exporters (Markdown, JSON, JSON Canvas)
     - the atomic save

     the Electron app; the demo script becomes a manual checklist.

     image files.

     (nativeTheme → data-theme) with no manual toggle. Since everything uses
     tokens, this costs almost nothing.

● I've written the implementation plan for the full WebAtlas build. It follows
  every default you accepted: one phased plan, DESIGN.md components ported to
  typed React files, Vitest only for pure logic, the coastal-adaptation sample,
  and dark mode that follows Windows.

  Plan: .claude/plans/webatlas-full-build.md

  How it's organised: 10 phases, each ending in a state where npm run dev still
  works. In build order:
  - scaffold plus spikes 1 and 2
  - the command layer
  - main-process storage and IPC
  - the app shell and home screen
  - the canvas
  - the browser pane and capture
  - the side panel, search and views
  - export, import and the sample
  - Organize, starting with spike 3
  - polish

  Every task has a validation command and is tied to one of 15 acceptance
  criteria. The last check is your demo script as a 17-step manual run, done 3
  times in a row. The pure-logic parts (storage, clustering, AI tool mapping,
  exporters) can be built alongside the UI work.

  Complexity: High. The plan adds up to about 6.9 hours against your 6-hour
  budget. Building those independent parts in parallel brings it back to about
  6. Solo, you'd need the cut list in the plan's Notes early; it names what to
  drop first and what never to drop.

  Things I found that change the architecture doc slightly (listed in the plan's
  Open Questions):
  - Popups: the webview new-window event the architecture relies on was removed
    in Electron 22. The plan catches popups in the main process with
    setWindowOpenHandler instead.
  - Hotkeys: Alt+A, Alt+H, Ctrl+K and Ctrl+L won't reach the app while focus is
    inside the webview. They go through Electron menu accelerators instead. The
    right-click "Add highlight / Add link to canvas" menu also handles text
    selected in PDFs, where the normal selection read doesn't work.
  - Small interface additions: thumb.save takes the workspace ID, plus a close
    handshake so nothing is lost on quit and a custom protocol to show
    thumbnails. Organize's group and tag tools also get a reason and confidence,
    because DESIGN.md requires every suggestion to explain itself.
  - Fonts: bundled locally rather than loaded from Google Fonts, so the demo
    works offline.
  - Haiku calls: strict tool schemas need no beta header. The calls leave out
    thinking and effort, and the tool-call loop stops after 3 rounds.

  Main risks:
  - transformers.js may not load inside Electron's main process (spike 2 covers
    the fallback).
  - Suggestion quality on topics the judge picks (spike 3 decides whether to
    ship typed relationships or groups only).
  - The sync between React Flow and the store, especially grouped cards whose
    positions are relative to their group.
  - The 0.9-hour overrun.

  Confidence of a one-pass build: 7/10. The logic is well specified and backed
  by the tests. The losses are likely to come from integration details in
  Electron and React Flow that only running the spikes will show.

  and address autofill feature (Autofill.enable, Autofill.setAddresses).
  Electron doesn't include that feature, so the requests are refused and logged
  as errors.

  Why they appeared twice: the timestamps are about 23 seconds apart (00:38:55
  and 00:39:18). That fits opening DevTools twice, once for each check in the
  checklist. They show up in the terminal when DevTools opens. Closing the
  window just made you notice them.

  Impact:
  - They only happen when DevTools is open.
  - DevTools can only be opened in development (npm run dev).
  - Users never see them, and they don't affect the app.
  - The E2E test "starts without console errors" watches the app's own page, and
    it passes.

  How this differs from the architecture doc (please confirm)

  1. Card colour is optional (color?: Cat), because a fresh card has no colour.
     The architecture lists color without saying.
  2. Ghosts have two extra fields: kind (group, link or tag) and title, which
     the suggestion cards need (DESIGN.md's GhostSuggestion).
  3. The session has two new fields: browserOpen and splitRatio, for your
     flexible layout. Every workspace gets a version number (version: 1), and
     the board is stored in the workspace (board).
  4. The command list is 22 kinds, not the plan's rough 20. I added
     removeComment (to undo addComment) and addGroups, a plain insert used when
     undoing a group deletion.
  5. Duplicate detection normalises the URL:
     - www. is removed from the host
     - tracking parameters (utm_*, fbclid, gclid and similar) are dropped, along
       with the #hash and a trailing slash
     - query parameters are sorted
     - every YouTube link form becomes youtube.com/watch?v=ID
  6. arXiv /pdf/ links count as PDFs even without a content type. The spike
     showed they have no .pdf extension.
  7. toggle-browser is a menu action, so Ctrl+B works even while you're typing
     inside the web page.
